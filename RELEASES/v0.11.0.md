# Kulyrax v0.11.0

## Status

Alpha. This release makes the file-backed stores (document, key-value, graph)
**crash-safe and batched**: a crash, an OS crash or a power loss no longer loses or
tears a projection, and each batch is made durable with one fsync instead of none.
It contains small **breaking changes** for code that embeds `kulyrax-core`, a new
**single-writer rule** for file stores, and a new minimum Rust version (1.89); see
[Upgrading from 0.10](#upgrading-from-010).

---

## Highlights

### Crash-safe file stores
Until now the file stores wrote each event straight to its data and guard files with
no fsync, and the source checkpoint was not fsynced either. After an OS crash or a
power loss, the checkpoint could survive while the projections it covered did not,
and those events were never projected again. A process crash in the middle of an
event could leave a new data file next to an old guard.

Now each file store writes a batch like this:

1. Every event is decided in memory, as before. A key written several times in a
   batch keeps only its final content.
2. The whole batch, data and guards, is written to one **batch log**
   (`.conduit/wal/<n>.log`, with a length and a CRC-32) and fsynced once.
3. The batch is applied to the per-key files, without fsync.
4. The source checkpoint is written: temp file, fsync, rename, directory fsync.
5. In the background, once the batches are 2 s old, a **sync point** fsyncs each
   file they touched (once per file), then deletes their logs.

At start-up, each file store replays any batch log still on disk before ingesting
anything. A torn newest log (a crash during its write) is discarded, and its events
are read again from the source. Details, costs and assumptions:
[`docs/file-store-durability.md`](../docs/file-store-durability.md).

Tested by crashing the real binary at each step of the commit path, by truncating a
log, by wiping every file not yet synced, and by killing it at random 20 times, each
time comparing every file with a run that never crashed.

### File stores commit once per batch
The file stores now implement `begin_batch` / `commit_batch` / `rollback_batch`. A
rolled-back batch leaves nothing on disk, and a failed event leaves nothing of
itself. Guards are cached in memory. On a store that starts empty, a guard that
isn't cached is known to be absent without reading the disk.

Throughput, 100,000 events, batch 5,000, one Windows laptop (internal baseline, not
a published benchmark):

| Store | v0.10 (excluded from Defender) | v0.11 |
|---|---|---|
| Document | 393 events/s | TBD |
| Key-value | 430 events/s | TBD |
| Graph | 360 events/s | TBD |

### Time per stage for the file stores
`kulyrax run`'s stage table has three new rows: `log` (writing and fsyncing the batch
log), `apply` (writing the per-key files) and `sync` (sync points, which run in the
background).

## Upgrading from 0.10

### Everyone
- **Rust 1.89 or newer** to build from source (was 1.88), for `File::try_lock`.
- Nothing to change in config or mappings. A file store's first start under 0.11
  creates `.conduit/wal/` and `.conduit/lock` in its root.

### Operators
- **One process per file store.** Each file store locks `.conduit/lock` when it
  starts. A second Kulyrax process on the same store directory now stops at start-up
  with "file store … is in use by another process". Two processes writing one store
  were never safe; now it is refused. Within one process, `kulyrax reload` keeps
  working. A document store and a key-value store can still share one root.
- Expect up to about 3 s of recent batches in `.conduit/wal/` while running. They
  are deleted at each sync point and at a clean shutdown. Don't delete them by hand:
  they are what recovery replays.
- If start-up fails with "batch log … is corrupt and newer batch logs exist", the
  disk returned bad data. A crash cannot cause this. Keep the logs for inspection,
  and rebuild the store from the event log.
- Each batch now costs one fsync per file adapter plus one for the checkpoint.
  Prefer large batches (the default 5,000) for file stores.
- Files written before 0.11 were never fsynced. A store that was running during an
  OS crash or power loss under 0.10 may hold torn files: rebuild it if in doubt.

### Embedding `kulyrax-core`
- `StageTimings` has three new fields, `log`, `apply` and `sync`, and `Stage` three
  new variants. Exhaustive matches and struct literals need them.
- New function `kulyrax_core::execution::stages::record`.
- New public module `kulyrax_core::adapter::file_store` (`FileStore`, `FileTxn`),
  the durable write path the file adapters share.
- File adapters you build yourself may call `prepare()` before `handle()`, as with
  every other adapter. If you don't, they prepare themselves on first use (lock and
  recovery) and keep working as before.
- `source::checkpoint::write_checkpoint` now fsyncs. It is slower: one fsync per
  call.

## Fixes
- **File stores: a projection could be lost after an OS crash or power loss** while
  its checkpoint survived, and a process crash mid-event could leave a data file and
  its guard out of step. See Highlights.
- **Source checkpoints are now durable** (fsync before and after the rename). Before,
  a power loss could lose or tear the checkpoint file.

---

## Known limitations
- MySQL, Redis, MongoDB, Neo4j and Elasticsearch still commit once per event;
  batching them and an Elasticsearch `_bulk` path are next.
- On Windows, a directory cannot be fsynced; renames rely on NTFS journaling its
  metadata in order (not verified with a power cut). Linux and macOS fsync the
  directories.
- File-store throughput is bounded by the cost of creating files: two per event
  (data and guard). On the Windows laptop used here that cost dominates. Numbers
  from a Linux machine will follow.
- Every number in `docs/ledger/` is an internal baseline from one Windows laptop.
- Kulyrax's own bookkeeping still uses pre-rebrand names (`conduit_projection_state`,
  `.conduit/`, `__ConduitGuard`).
- Release binaries are not code-signed.
